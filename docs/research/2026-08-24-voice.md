# Live mode: voice on an isomorphic canvas

**24 August 2026; revised 11 September 2026**

Voice is another input surface over isocan's existing operations. It must not
become a second writer, an alternate permission system, or the only way to do
something to a canvas.

## What changed on 11 September

The August argument put the provider socket in the daemon and barred
non-undoable operations from voice. **Both decisions are superseded for the
UI build:**

1. **The browser holds the Gemini Live session.** The daemon retains the API
   key, authorizes and mints a short-lived provider token, and remains the
   operation executor. Socket custody does not decide where state is written:
   a browser tool call still goes through the same daemon as a click or CLI
   command.
2. **Voice has an agent's authority, neither more nor less.** Offer the full
   permitted public operation vocabulary, with the same validation, actor
   binding, admission, rung checks and confirmation steps. No voice-specific
   destructive-operation ban; no voice-specific privilege.
3. **Operation authority and provider-spend authority are different.** The
   initial request for owner-only minting exposed a missing boundary: local
   agents can share the owner's credential. The subsequent decision is to
   build **Tier 0: local-machine trust, duration/rate/uses bounded, with a
   usage estimate**. It does not distinguish an owner's browser from an agent
   running as that owner. Human-presence and hosted owner-credential gates
   are later tiers, not labels substituted for authentication.

**Provenance and scope.** The August draft used second-hand API material after
certificate failures. Primary Google, Chrome and W3C material was retrieved
successfully for this revision. Sources are linked below and facts are dated,
not a claim that a model is enabled for a particular account. No API key,
provider session, microphone capture or paid audio was used for this research.

The reviewed `packages/voice` prototype is on `feat/voice-interface` at
`5651df9f`, **not** upstream `main` at the inspected `ed8efe0c`. It proves a
bounded keyless CLI/daemon path, declared audio formats, conversion fixtures
and provider setup-acknowledgement handling. It does not provide microphone
capture, playback or this browser UI. Reuse that package on a fresh upstream
base; retain its CLI as the headless harness. The registration PRs did not
merge the implementation.

Keep quick gestures quick and dispatch lengthy work through ordinary threads.
That remains a useful interaction design on either model; it is not a reason
to remove operations from voice. `item.add` can attach already-prepared content
quickly. Generating that content may take minutes. The operation name alone
does not classify the work's duration, and the old “26 of 28” count is retired.

A slow request can create or reply to a thread, then return promptly. **It does
not automatically wake every parked agent.** At `ed8efe0c`, the owner-only
summons change (`0a3e9e7a`, #238) makes the rc enforce each agent's `listen`
policy, defaulting to its owner. `server/rc-holds.ts` advertises those policies
and routes add-agent asks to an rc the asker owns; only the rc starts a turn.
A separately attributed voice actor does not become that owner by posting a
comment. The ordinary listening policy must allow it; never impersonate the
person to make dispatch work.

### Wire, audio and lifetime

The [WebSocket guide](https://ai.google.dev/gemini-api/docs/live-api/get-started-websocket)
and [API reference](https://ai.google.dev/api/live) describe a bidirectional,
stateful connection. Send `setup` first and wait for `setupComplete` before
sending input. Socket OPEN alone is not readiness.

- Input is little-endian, mono PCM16, natively 16 kHz. The
  [capabilities guide](https://ai.google.dev/gemini-api/docs/live-guide) also
  says the API resamples other input rates; the MIME rate must describe the
  **actual bytes**, not a preferred rate written onto unconverted audio.
- Output is little-endian PCM16 at 24 kHz. Browser capture and playback may
  use different device rates. Reuse the package's format-aware boundary and
  both-direction byte tests rather than hard-coding the client's rate.
- The existing streaming linear interpolator is prototype-quality: no
  anti-alias filter, and an unfinished lookahead tail is discarded at reset or
  turn end. Those tests are not production audio-quality evidence.
- Input and output transcription are setup options. Handle all server content
  parts, `interrupted`, turn completion and tool-call cancellation. Interrupt
  means clear queued playback as well as stop future tool dispatch.
- The [session-management guide](https://ai.google.dev/gemini-api/docs/live-session)
  currently describes 15-minute audio-only sessions without compression,
  roughly 10-minute connections, and resumption handles valid for two hours
  after session termination. Compression and resumption address different
  limits. The August “resumable within 24h” statement is withdrawn. These are
  provider-documented limits, not measured guarantees for this UI.
- A disconnect, token expiry or `goAway` needs an explicit UI state. Resumption
  must not replay tool effects. Stopping is not rollback: a native operation
  already invoked may finish, while undispatched work must be revoked.

### The browser's ephemeral token

The [ephemeral-token guide](https://ai.google.dev/gemini-api/docs/live-api/ephemeral-tokens)
documents this path:

1. The browser authenticates to **isocan**, not to Gemini with OIDC. On a
   hosted deployment, require a badge carrying a server-verified email
   attestation: the existing meaning of an authenticated, signed-up user.
   A caller-supplied email or harness name cannot satisfy this check. Local
   installs use the explicit machine-trust posture described under Tier 0.
2. The daemon calls
   `POST https://generativelanguage.googleapis.com/v1beta/auth_tokens`, using
   a **system API key held server-side**. The deployment operator pays for
   users' sessions. Sign-up gating and per-user limits therefore protect the
   operator's quota; they do not bill each user's own Gemini account.
3. The daemon returns the short-lived token, not the API key. The browser
   keeps it in memory and connects to:

   ```text
   wss://generativelanguage.googleapis.com/ws/google.ai.generativelanguage.v1beta.GenerativeService.BidiGenerateContentConstrained?access_token=<short-lived-token>
   ```

This issuer decision reuses the identity desk: isocan borrows a verified
identity and records the attestation on its badge; it does not create a new
account service or ask Gemini to accept isocan's sign-in token. It excludes
unauthenticated outsiders, **not an agent sharing an authenticated user's
badge**. Per-actor spend separation remains a follow-up.

The current defaults are one use, **one minute to start** a new session
(`newSessionExpireTime`) and **30 minutes to send messages** (`expireTime`).
They are separate clocks. Choose explicit, short limits rather than inheriting
those defaults unnoticed. Tokens can constrain session configuration, including
the model. The guide documents resumption with the same token inside its
validity window even with `uses: 1`; “one use” is not a ban on that resumption.

The browser token is extractable by code controlling the page. Short lifetime
and constrained setup reduce that exposure; they do not make it secret from
the browser. Do not persist it in local storage, transcripts, logs or error
messages. Closing the socket is not evidence of server-side token revocation.
**A Google ephemeral token does not authenticate a caller to our mint route.**
That is a separate boundary, below.

## Permission UI: the shipped element, with a fallback

The [Chrome article](https://developer.chrome.com/blog/usermedia-html-element)
describes `<usermedia>` shipping in Chrome 151; the dedicated `<microphone>`
element is on its roadmap. The [W3C media-elements explainer](https://github.com/w3c/mediacapture-extensions/blob/main/media-capture-elements-explainer.md)
describes both, but an explainer is not proof that both are implemented.

A read-only probe of the existing MCP browser reported
`HeadlessChrome/152.0.0.0`: `HTMLUserMediaElement` existed, while
`HTMLMicrophoneElement` did not. The former exposed `stream`, `setConstraints`
and `onstream`/`onerror`/`oncancel`; creating `microphone` yielded an unknown
HTML element. **No permission was requested or capture exercised by this
probe**, and it is not a cross-browser compatibility test.

The UI should have a bottom-left microphone affordance, alongside the existing
canvas controls, and acquire audio only following an explicit user action:

- Feature-detect the supported element API. For `<usermedia>`, configure
  **audio only** before it is usable, then consume the delivered stream. Its
  unconstrained default includes video; never request the camera incidentally.
- Do not set `autostart`. In this API permission approval can itself start
  hardware capture. Do not obscure or imitate the browser-controlled consent
  surface to obtain the desired visual treatment.
- Where the element is unavailable, use a labelled button invoking
  `navigator.mediaDevices.getUserMedia({ audio: true, video: false })` from
  the click, in a secure context. Explain denial, dismissal, missing devices
  and unsupported capture without retrying or prompting on page load.
- Keep permission, capture, provider connection and billable-session state
  distinct. Microphone permission does not authorize provider spend. Mute is
  not Stop: muting does not necessarily close a billable connection.
- Stop must release media tracks, close playback resources, revoke pending
  work and disconnect. Navigation, hidden-tab handling, connection failure and
  permission loss need explicit lifecycle coverage, not a permanently glowing
  mic with no working session.

Browser evidence must name the browser and element actually exercised. A
permission denial test, fake-device capture and a spoken-simulated turn are
useful but separate evidence. None proves real microphone quality, live
speech recognition or a successful paid provider exchange.

## Authority: same operations, real confirmation

The single-writer engine remains the authority. Tools call existing gestures
or operations through it, with a distinct voice actor; they must not take the
person's ambient `connect()` identity. Reuse native gestures such as grouped
movement where those preserve attached annotations and undo semantics.
Internal-only operations do not become public merely because they appear in
a TypeScript union.

The source census at `ed8efe0c` found:

- `packages/core/src/ops.ts` defines the vocabulary; `server/http.ts` handles
  `/api/ops`, admission and the read/edit/own ladder. The engine checks badge
  claims and operation-specific validation. Read-only admission cannot become
  edit authority through a tool schema.
- The CLI's canvas deletion requires `--force`; `TrashPanel.tsx` uses a
  two-step “can't be undone” confirmation for `trash.empty`.
- **Those destructive confirmations are client-side conventions.** The
  current daemon does not require a separate approval receipt for
  `trash.empty` or `project.delete` from an otherwise authorized editor.

Mirror those actual confirmation steps in voice, without inventing a new
server approval system. **The operation waits for the person.** The model
asks, the UI states the exact target and consequence, and the person confirms
or cancels. A model-supplied `force: true`, a tool argument named `confirmed`,
or the model's own spoken “yes” is not confirmation. If a spoken response
cannot be distinguished from generated content with adequate confidence, use
an explicit person-operated confirmation control. Do not dispatch the op and
ask afterward. A refusal or cancelled confirmation leaves state unchanged.

This includes non-undoable actions; the old blanket voice denial is removed.
The same vocabulary does not mean every action is undoable. Replay reproduces
accepted canvas effects without audio or another model/tool invocation, while
non-undoable effects remain non-undoable.

## Provider-spend boundary inventory

**On one machine under one OS user, nothing a process says distinguishes an
agent from the owner's browser.** An agent with the owner's access can read
those files, open those sockets and send those strings. A genuine separation
needs a protected credential or a different trust domain, not a better label.

The [identity desk](../projects/multiuser/identity-desk.md) already supplies
badges, actor binding, attestations and grants such as `email:<addr>`.
`server/attest.ts` verifies Identity Platform ID-token signatures and binds
issuer/audience to the configured project, checks expiry, and requires a
verified email. Configuration selects a real verifier; it does not turn an
asserted email into an attestation. Verified email identifies a person, not
which of that person's processes may spend. Reuse these mechanisms rather
than introducing an unrelated identity service.

| Candidate signal at `ed8efe0c` | What the inspected code establishes | Owner-only mint boundary? |
| --- | --- | --- |
| Actor harness / `PERSON_HARNESSES` | `core/claims.ts` derives the harness from `op.sessionKey`; `/api/ops` in `server/http.ts` passes the caller's claim to `engine.claim`. It is a recorded classification. | **No: label-only.** A stored caller-selected prefix is not an unforgeable person credential. Unknown kinds also read as people for display/counting, not authorization. |
| Presence `kind: "web"` | `server/ws.ts` labels socket-born sessions; the HTTP session route cannot request that kind. | **No: transport label.** A non-browser client can speak WebSocket too. |
| `Origin`, `User-Agent`, request actor/name | Header policy can protect against ambient-cookie CSRF; the engine can check that a badge claims the named actor. | **No by themselves.** Headers and body labels do not establish which holder is spending. Keep CSRF checks, but do not call them identity. |
| Existing badge token | `server/badges.ts` mints a random secret, stores its SHA-256 hash and compares the presented secret in constant time. | **Secret-backed badge authentication, not the requested owner-only signature.** It proves possession. `core/claims.ts` explicitly describes local agents sharing the CLI badge; that shared credential cannot distinguish its holders. |
| Actor binding and own rung | `/api/ops` supplies the authenticated badge ID to the engine; `claimsActor` checks its claims. Existing owner/rung helpers protect ordinary product actions. | **Useful checks, not sufficient separation.** A shared badge may speak for several actors. Naming the owner's actor does not isolate the caller from an agent holding that badge. |
| rc owner/listen policy | `server/rc-holds.ts` routes owner-scoped asks and advertises policy; the rc decides which speaker starts a turn. | **No new credential.** Listening policy does not supply a provider-spend authorization secret. |
| Verified-email attestation | The identity desk describes verified attributes and grants, including already-built email-attestation work. | **Person identity, not a spend grant.** Reusing it still requires an owner-bound credential that agents cannot acquire through their existing authority. |

**Conclusion:** no unforgeable owner-versus-agent **spend credential** was
found for the shared local-badge case. That proves shared authority, **not**
that an existing Gemini billing endpoint or current provider spending was
observed. It is a product-level custody issue as well as a voice-design input.

There are useful built mechanisms to extend, with their actual scope intact:

- `POST /api/projects/:id/passes` and `mintPass` provide an existing
  canvas-scoped, redeem-once secret pattern, with a hashed secret and
  `requireActor` checking the presenting badge. A pass is not a provider
  token and that check does not separate holders of a shared badge.
- `server/content-auth.ts` already signs and verifies HMAC-scoped content-read
  URLs. `server/attest.ts` verifies RS256 sign-in tokens. Cryptographic
  primitives are built; an owner-only voice-spend grant is not.
- `server/meter.ts` already provides a token-bucket **mint-count** limiter.
  It is in-memory and resets on restart; its own comments document key
  eviction and proxy-address assumptions. Reuse the limiter, not a fictional
  monetary-budget guarantee. Voice-specific mint records and usage reporting
  still need implementation.

### The three tiers

**Tier 0 — build the local UI first, with honest limits.** The trust boundary
is the machine, not person-versus-agent. Keep ordinary badge, actor, admission
and own-rung checks for minting, but acknowledge that a process holding the
owner's credential shares that authority. Require explicit operator activation,
short provider-enforced token expiry, a small new-session window, one session
use and constrained model/setup. Limit mint frequency, record each mint
without secrets or audio, and show elapsed time, expiry and usage estimates.
Do not expose this local posture as a hosted owner-only issuer.

**These are duration/rate/uses bounds, not a hard dollar cap.** The inspected
Google AuthToken schema documents `expireTime`, `newSessionExpireTime`, `uses`,
`fieldMask` and `bidiGenerateContentSetup`. Its expiry rejects later provider
messages, and locked setup constrains the connection even when its holder
ignores the UI. A holder cannot extend those fields without obtaining another
token. The local limiter governs new mint attempts, subject to its stated
restart and trust assumptions.

No per-session monetary/aggregate-token budget or immediate AuthToken
revocation method was found in the inspected Live API reference and token
guide. `maxOutputTokens` caps a response, not the session total. Client-reported
`usageMetadata` is a usage observation, not an authoritative billing meter.
**Stop closes the cooperating client's socket and revokes local pending
operations; it does not remotely revoke Google's already-issued token.** An
uncooperative holder may continue within its provider-enforced validity.

This is a consequence of browser-held transport: the daemon does not see an
authoritative usage stream or control that provider socket. A real spending
cap needs provider-side enforcement or a different metering architecture.
Daemon-relayed transport would improve observability and cutoff control, but
even that needs defined accounting and in-flight-charge handling before being
called a hard dollar guarantee. Do not silently reverse the browser-session
decision to claim a cap.

**Tier 1 — protected human-presence authorization.** A future passkey/WebAuthn
flow can require a fresh challenge and authenticator-mediated presence or
verification using a credential unavailable to the agent. Bind approval to the
specific session request, not a reusable “human” bit. This plumbing is not
built. A device-flow code is another proposed ceremony, but printing a code
and accepting it in the same accessible browser is **not by itself** a new
trust boundary; the confirmation must rely on something the agent cannot
approve or replay alone. Do not describe an ordinary click or code echo as
proof of a human.

**Tier 2 — hosted identity, then separate actor credentials.** The first
hosted issuer gate is the existing email-attested badge, as decided above,
with per-user limits on the operator-funded system key. `verifyIdToken`
verifies the upstream sign-in signature when the attestation is obtained;
ordinary badge requests still authenticate an opaque bearer. Do not claim
that each mint request already carries a signed, actor-isolated credential.

Stronger owner-versus-agent separation needs a different trust domain: a
signature-verified, short-lived, session-scoped spend authorization bound to
the **owner's credential and actor**, with separate agent credentials that
cannot obtain or sign it. Reuse existing signature and attestation patterns.
Key custody, issuance, replay protection and revocation for this new purpose
remain design/build work. An email attached to a shared badge is not that
separation.

## What the canvas contributes

Speech needs references for “this”, “those two” and “the other one”. Reuse the
speaker's selection and cursor, title resolution, and a thread's `comment.items`.
If they disagree or the target is ambiguous, ask rather than guessing. Shared
presence supplies useful references; it does not prove speaker identity or
permission to act. Capture the relevant selection with the request instead of
letting a later pointer movement change an already-confirmed target.

Keep three kinds of trace separate:

| Trace | Intended home |
| --- | --- |
| Live transcript and listening state | Ephemeral UI/presence, with explicit sharing; not an automatic stream of thread comments. |
| A decision | One ordinary comment after the person checks the readback. |
| Canvas actions | Ordinary operations, under the voice actor, with the existing undo/replay behavior. |

One Live session should hold the conversational floor, rather than opening one
billable listener for every parked agent. Handing work to another agent uses
ordinary threads and that agent's listening policy. Multi-voice selection and
distributed floor ownership remain design work, not features of the accepted
CLI prototype.

## What to build and prove next

Finish this note and the UI/token/tool-authority plan before implementation.
The plan must specify Tier 0's local trust assumptions and genuine provider
constraints, locate the daemon endpoint and describe the bottom-left permission
and confirmation flows. Use the existing attested-email gate for the hosted
issuer; keep protected human-presence and per-actor spend authorization
separate from that first build. Then extend `packages/voice`
for browser transport, capture and playback while retaining the CLI harness.

Use isolated synthetic canvases and fake devices for permission/lifecycle and
wire fixtures. Drive an observable canvas action in a real browser, label the
spoken simulation, and show denied permission, refused unauthorized minting,
rate/expiry/uses constraints, real confirmation, setup acknowledgement and
cleanup as well as success. Include the accepted Tier 0 counterexample: an
agent sharing the owner's credential is not distinguishable from that owner.
Review the exact committed candidate with a different model. Keep real
microphone activation, credentials, audio egress and provider spend behind
explicit owner activation; this note authorizes none of them.

A useful voice surface does not merely narrate actions, flood a thread with
transcripts, listen without the room knowing, or keep billing after a user
thinks it has stopped. Those are acceptance failures, not polish for later.
