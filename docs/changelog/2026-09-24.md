### feat(hooks): a pre-push gate — types and the fast suite, chained where git looks (isocan-1j1)

`cdbdbb9`

isocan had no test gate on push: the hook git actually ran was Beads' own, so a
push could carry a red suite and nothing on the way out said so. It cost a night:
a red typecheck and two suite failures were found by a person running gates by
hand while holding an exclusive push slot.

**Why the gate is `scripts/pre-push.sh` and not a hook file.** Hooks do not
travel — `.git/hooks` and `.beads/hooks` are both untracked — so the tracked half
is the script, and `scripts/install-hooks.mjs` decides where it goes. Doing that
found the second reason there was no gate: `core.hooksPath` is `.beads/hooks` on a
beads machine, which SHADOWS `.git/hooks` completely, so the repo's own hook had
never once run. So the installer now CHAINS our hook into one it did not write
instead of refusing it, and `scripts/hooks/pre-push` (the generated-doc check,
still refusing first) chains the gate.

**The fast lane, deliberately**: `npm run typecheck`, then `npm test`. The deep
lane stays CI's — a five-minute suite on every push is a gate people learn to
`--no-verify`.

**`GIT_DIR` is unset before the suite, and that line is not decoration.** Git runs
hooks with `GIT_DIR` set, so a test that spawns git in a scratch directory has its
commands applied to the repository being pushed. Measured on this hook's first
green attempt: `fatal: cannot force update the branch 'main' used by worktree at
'/home/paulkinlan/isocan'` — `test/nightly-prs.test.ts` doing `git branch -M main`
in a temp directory that had inherited the hook's `GIT_DIR`.

**Verified, and the verification is the evidence**: with a deliberate type error
in a tracked file, `git push --dry-run` was refused by the hook git actually runs
(`[pre-push] REFUSED: typecheck is red`); with it reverted, the gate passed
typecheck and refused on the suite — for two reds that are NOT this change's
(`test/ports.test.ts` and `packages/web/test/echoed.test.ts` both fail when run
outside any hook too), which is the gate reporting main's state rather than its
own. Reported to coord; pushed with `--no-verify` and that reason stated.

### test(voice): chunk invariance is exact at 48 kHz and one LSB at 44.1 kHz (isocan-xsh.10)

`30de6d0`

A source probe found that a 44.1 kHz sine pushed whole and pushed in chunks
[128, 3, 77, 256, 1, 511] emits the same 32,013 samples with exactly one
differing by one PCM16 LSB — and the strict byte-equivalence assertion against
that was RED. Reproduced here before asserting anything: 32,013 = 32,013, one
differing sample, max delta 1, at index 22,981 (2265 whole, 2266 chunked); the
same signal at 48 kHz emits 32,012 with zero differences.

The difference is arithmetic, not a broken resampler: 44100/16000 = 2.75625 is
not an integer, so a chunk boundary can leave a fraction of a window behind, and
float→PCM16 rounding is not associative — the same sum can land either side of a
.5 LSB step. So the test asserts the strongest thing that is TRUE at each rate
rather than the same thing at both:

- **48 kHz (ratio 3): bit-identical** — the same sample count and
  `{differing: 0, maxLsb: 0}`, strictness where strictness is achievable;
- **44.1 kHz: the same sample count, at most one LSB, at most two differing
  samples** out of 32,013 — a bound carrying its measured numbers, so a reader can
  see what "justified" means rather than taking a tolerance on trust;
- and the **length is held exact across chunk sizes [1, 7, 128, 1024, 88237]**,
  which is the part a dropout or an off-by-one in the carry would break.

**Falsified twice, and the first attempt taught the shape of the claim.** A
*systematic* mutation (every positive sample one LSB low) leaves these tests green
— correctly: they assert chunk INVARIANCE, not absolute level, and a whole-buffer
error cancels in a whole-versus-chunked comparison. The mutation that bites is
chunk-dependent: dropping the fractional phase at each push reddens the length
sweep (`chunk size 1 lost or gained a sample: expected 44118 to be 32013`) and the
44.1 kHz bound, while the 48 kHz exact case stays green, because an integer ratio
has no fraction to drop. Both facts are in the test's own doc comment.

### fix(voice): a muted pause past a second flushes the stream (isocan-xsh.8.6)

`44827f1`

Measured on a real page: Mute stopped PCM for 1.5s while the Live session stayed
open, and `realtimeInput.audioStreamEnd` was never sent. Under automatic VAD —
the default this harness runs with, and it never disables it, so manual
`activityStart`/`activityEnd` are not the mechanism here — the Live capabilities
guide's answer to a paused stream is that frame; without it the provider holds
cached audio it has not decided about.

- `AUDIO_PAUSE_FLUSH_MS = 1000`, exported so the test and the code share one number.
- the live session tracks `streamOpen` (set when a frame goes up) and gains
  `endAudioStream()`, which sends `realtimeInput.audioStreamEnd` once per pause,
  gated on `setupDone` and an open socket exactly as every frame is.
- mute schedules the flush; **unmute and end cancel it** — a pause shorter than the
  window is a breath, not a pause — and the next frame after a flush begins a new
  segment, so unmute needs no matching "start": under automatic VAD the audio is
  the start.

The test rides the fake provider socket the suite already drives: a frame goes up;
one pause past the window produces exactly one `audioStreamEnd`; a second pause
produces a second and no more; a pause shorter than the window produces none (its
timer is cancelled); capture carries on afterwards. **Falsified rather than
asserted**: with the flush removed the test fails with
`one pause, one end: expected +0 to be 1`.

Verified: this file 91/91; `npm run typecheck` exit 0; fast lane 5910 passed with
only the by-design review-queue red; deeplist guard 10/10.
