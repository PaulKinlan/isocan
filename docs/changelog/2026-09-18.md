# 18 September 2026 — A stranded claim, and the wrong remedy printed beside it

The `roadmap-sync` timer had been failing for eight days. Its canvas, Roadmap
Test, was frozen at `434c9198` (10 Sep) while `origin/main` had moved 98
commits past it. The reason was one line in the service's own stderr:

    no actor is claimed under session "cron:roadmap-sync" — claim it once:
    ISOCAN_HARNESS=cron ISOCAN_SESSION_ID=roadmap-sync isocan identity --name "Your Name" --session

The actor *was* claimed. `Roadmap Sync` (`usr_AgRvjzUbIN`) had been claimed
under that exact key on 10 September — and the claim was still on the desk,
held by `bdg_f9YL8cthAI`. This machine re-badged on 12 September; the live
badge `bdg_ep0NQZDaZC` held five claims and not that one, and the migration
shelf was empty, so there was no legacy row left to adopt. The claim had not
been lost. It had been stranded on a badge nobody holds.

That is the case `noIdentityHere` was written for, and it says so plainly: the
identity IS configured, it is just not reachable from here, and `--name` would
mint a stranger wearing the same name and leave the history behind — "the
precise mistake `--as` exists to prevent". The ambient walk got that answer.
A script stating its own identity did not, because `connect()` printed a fixed
gesture and never asked the desk anything. So the timer's error advised the one
recovery that would have made the damage permanent: a second `Roadmap Sync`,
refused as name-taken, or admitted and splitting every later version and every
`undo` across two actors.

`connect()` asks now. The explicit-identity refusal looks up
`/api/actors/orphaned` for the one key the caller stated — key-scoped, so the
answer can never be a roster — and when that key is claimed on a badge this
machine no longer holds, it names the actor and prints `--as <actorId>` instead
of `--name`. A home that cannot answer degrades to the old generic gesture
rather than failing the refusal. The helper is private to `connect.ts` on
purpose: the API ceiling in `test/entry.test.ts` counts names a caller outside
the package needs, and this one has exactly one caller, inside it. Nothing
asserted the old message, and the new test is red without the fix — it
reproduces the eight-day stderr verbatim.

The recovery itself was the daemon's own sentence, run once:

    ISOCAN_HARNESS=cron ISOCAN_SESSION_ID=roadmap-sync isocan identity --session --as usr_AgRvjzUbIN

The timer's next scheduled fire, eight seconds later, did the rest: 109
operations in 90 seconds, every one of them stamped `Roadmap Sync`
(`usr_AgRvjzUbIN`) and none anonymous, 56 documents rewritten and 30 cards
added, the canvas caught up to `a770255c`. Checked against the repository
rather than against the script's own log: all 103 documents the current
`docs/ROADMAP.md` links now match `origin/main` byte for byte, by blob hash.
One card did not move and should not have — `docs/projects/memory/design.md`
left the roadmap table at `b5755f08`, and a file that leaves the roadmap
leaves its card behind, because nothing here deletes. The fire after that ran
quiet in 1.5 seconds: 103 tracked, 0 changed, exit 0.

The wider lesson is the part worth keeping. A refusal that names a remedy is
only as good as the remedy, and this one was confidently wrong for the single
case most likely to reach it — a long-running script whose badge outlived
itself. The desk already knew the truth; the door just was not asking.

## Eighteen commits that were already written, and one bug that was two

Most of what landed today was not written today. Six branches had been sitting
finished and unmerged since 10–11 September — transportable compute, the browser
surface, the roadmap canvas, watched files, static snapshots, the voice design —
and a sweep that went looking for beads which read as open while done found the
mirror image instead: work that was done and had never landed. So the day's work
was mostly reconciliation, and the interesting part is how the same thing kept
happening in different directions.

`docs/roadmap-canvas` had a commit whose whole content was a generator fix: a
row's link has to resolve from the directory the page lives in, so `href()`
strips a `docs/` prefix that sent all 74 links to `docs/docs/…`. That fix is
already in main. It landed independently, weeks ago, from somewhere else. The
cherry-pick therefore had nothing to carry but a regenerated page — and the
commit message it arrived with described a change that was no longer in it, so
the message was rewritten rather than left to claim credit.

The voice design went the other way. It was written on 11 September for a
`packages/voice` you started with `isocan voice`; what shipped is
`packages/voice-agent`, reached by `isocan rc` with `--acp`, plus a browser
module at `packages/modules/talk`. The doc set sat on its branch saying "phase 1
in progress" the whole time the thing was being built and verified underneath it.
Landing the branch would have been actively wrong — it carries the prototype main
replaced, so it would have put a second dead voice package beside the live one.
What landed is the docs commit alone, in a directory named after the package that
shipped, with the dated provider audit left byte-for-byte intact (a citation
quietly updated to look current is worth less than one honestly dated) and a
reconciliation table above it naming every divergence with the file and line that
decides it. Status `partial`, with the score in the front matter the roadmap
reads, so it cannot drift.

Then the one that was two bugs wearing one bead.

The voice harness gated audio on `socket.readyState !== 1` — an open socket, not
a ready provider. Measured on the real wire before the bead was filed: 192 of 208
frames went up before `setupComplete` on a keyless run, 128 before
acknowledgement on a real key, 48 page frames dropped while the transport was
opening. And the frame counter sat on the line immediately *after* that guard, so
fixing the gate alone would have made every frame it refused unmeasurable. Two
beads, one coupling, one change.

The cause underneath was plainer than either bead said. Five counters —
`pageAudioInFrames`, `pageAudioInBytes`, `providerAudioOutFrames`,
`providerAudioInFrames`, `pageAudioOutBytes` — were declared, printed by a timer
every three seconds, and never incremented anywhere in the file. The periodic
"live streaming throughput" line was a printout of five permanent zeros, which is
exactly what the real-provider control reported: 3904 frames up, 17 parts down,
all periodic stats zero. Nobody had wired them because nothing ever read them
back. Four are wired now at the two places audio actually crosses; the fifth is
deleted, because the session that did the sending is the authority and the line
asks it.

Two things the fix turned up that were not in either bead. `git grep
realtimeInput` found the same defect in a second place — the browser module's
microphone capture gating on `readyState === WebSocket.OPEN` alone — so a
harness-only fix would have left the page still sending into the setup window.
And an existing test *asserted the defect*: "speaks the wire: setup first, then
audio up" sent audio into an open-but-unacknowledged socket and expected the
frame on the wire. A suite that encodes the bug is why the bug looks covered, and
this is the third time that shape has turned up here.

Everything was reproduced before it was fixed. Five tests, red on untouched main,
each failing for the reason that matters — the decisive one with all five frames
already on the wire. The browser half is a source assertion rather than a
measured capture, because that test file has no DOM harness, and it is recorded
as the weaker thing it is.

The night shift got two corrections out of the same sweep. `changelog.yml` had no
reuse guard, so a second run on the same day pushed a divergent history over a
branch that already existed and was rejected — a red run, and the only way to
retry was a blanket `--force` over a page a writer might already have edited.
`grade.yml` has carried the fix for the identical problem all along, so the
pattern was copied from the sibling workflow and the force deliberately was not:
a generated page can be rebuilt, a writer's sentence cannot. And AGENTS.md's
claim that PRs opened by `GITHUB_TOKEN` "fire no `pull_request` workflows" is not
what GitHub says — they do fire, for `opened`/`synchronize`/`reopened`, into an
approval-required state. The correction strengthens the conclusion rather than
weakening it: the runs exist and could be approved, so running the suite in the
merge step is a choice this repo makes about three in the morning, not a law of
the platform.

Lastly, a filter that had no test. Six CLI test files stopped asserting
`stderr === ""` because Node 26's `module.register()` deprecation warning lands
in the runtime's stderr and reads exactly like a product red. The acceptance was
"six files pass on Node 26" — untestable from a Node 24 machine, where the
runtime emits nothing and the six pass either way, proving nothing. So the filter
itself got the test: the runtime's envelope goes, and a product line that happens
to say "warning" survives. A filter that stripped too much would have turned six
loud tests into six silent ones, which is worse than the bug it was written for.
